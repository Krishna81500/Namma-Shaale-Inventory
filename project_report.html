2. Project Overview

2.1 Project Background

"Namma Shaale" (meaning "Our School" in Kannada) is an Android application developed to digitize asset management processes in government schools. Traditional paper-based systems often lead to inefficiencies, loss of data, and poor tracking of school resources. This app addresses these issues by providing a mobile-first solution for asset inventory, condition monitoring, and reporting.

The project was developed as a demonstration of modern Android development techniques, incorporating the latest frameworks and best practices. It serves as a practical example for students learning mobile application development.

2.2 Project Objectives

The primary objectives of the Namma Shaale project are:

  • Digitize school asset management: Replace manual paper-based systems with digital tracking
  • Provide real-time tracking: Enable instant access to asset conditions and locations
  • Enable efficient issue logging: Streamline the process of reporting and resolving asset problems
  • Generate AI-powered audit reports: Use artificial intelligence to create comprehensive reports
  • Manage school staff and attendance: Include human resource management features
  • Ensure data security: Implement proper authentication and data protection
  • Demonstrate modern Android development: Showcase current best practices and technologies

2.3 Target Users

The application is designed for multiple user roles in educational institutions:

  • School Administrators: Overall management and reporting
  • Teachers and Staff: Daily asset usage and issue reporting
  • Facility Managers: Maintenance and condition monitoring
  • Government Education Officials: Audit and compliance checking
  • IT Support Personnel: System maintenance and data management

2.4 Scope and Limitations

In Scope:

5. System Architecture

5.1 Architectural Pattern

The application follows the MVVM (Model-View-ViewModel) architectural pattern, which is recommended for Android development:

  • Model: Data classes and repository layer handling data operations
  • View: Compose UI components (screens) responsible for displaying data
  • ViewModel: Business logic and state management, acting as bridge between Model and View

5.2 Layered Architecture

The system is organized into distinct layers for better separation of concerns:

┌─────────────────┐
│   UI Layer      │  (Screens, Composables)
│                 │  - LoginScreen, DashboardScreen
│                 │  - Navigation logic
├─────────────────┤
│ ViewModel Layer │  (State management, business logic)
│                 │  - AssetViewModel
│                 │  - StateFlow for reactive updates
├─────────────────┤
│ Repository Layer│  (Data access abstraction)
│                 │  - AssetRepository
│                 │  - Clean API for data operations
├─────────────────┤
│   Data Layer    │  (Room DAO, Local/Remote data)
│                 │  - AppDatabase, AssetDao
│                 │  - GeminiReportGenerator
└─────────────────┘

5.3 Data Flow Architecture

The application implements unidirectional data flow:

  1. User Interaction: User interacts with UI components (View)
  2. Event Handling: UI triggers ViewModel methods with user actions
  3. Business Logic: ViewModel processes requests and calls Repository
  4. Data Access: Repository accesses local database via DAO
  5. Data Retrieval: Data flows back through Repository to ViewModel
  6. State Update: ViewModel updates StateFlow, triggering UI recomposition
  7. UI Update: Compose automatically updates the UI based on state changes

5.4 Component Architecture

Single Activity Architecture: The app uses a single MainActivity with Compose Navigation for screen management, reducing complexity and improving performance.

Repository Pattern: AssetRepository provides a clean abstraction over data sources, making it easy to switch between local and remote data sources in the future.

Observer Pattern: StateFlow implements the observer pattern for reactive UI updates without callback hell.

7.3 Detailed Entity Analysis

7.3.1 Assets Table

@Entity(tableName = "assets") data class Asset( @PrimaryKey(autoGenerate = true) val assetId: Long = 0, val name: String, val category: String, val location: String, val quantity: Int, val purchaseDate: String, val conditionStatus: String, // GREEN, YELLOW, RED val photoUri: String? = null )

Fields Explanation:

  • assetId: Auto-generated primary key
  • name: Asset name (e.g., "Dell Desktop PC")
  • category: Classification (Electronics, Furniture, etc.)
  • location: Physical location in school
  • quantity: Number of items
  • purchaseDate: Acquisition date
  • conditionStatus: Current condition (GREEN/YELLOW/RED)
  • photoUri: Optional photo reference

7.3.2 Issue Logs Table

@Entity( tableName = "issue_logs", foreignKeys = [ ForeignKey( entity = Asset::class, parentColumns = ["assetId"], childColumns = ["assetId"], onDelete = ForeignKey.CASCADE ) ] ) data class IssueLog( @PrimaryKey(autoGenerate = true) val issueId: Long = 0, val assetId: Long, val description: String, val severity: String, // Low, Medium, High, Critical val dateReported: String, val repairStatus: String, // Pending, In Progress, Resolved val photoUri: String? = null )

7.3.3 Condition History Table

@Entity( tableName = "condition_history", foreignKeys = [ ForeignKey( entity = Asset::class, parentColumns = ["assetId"], childColumns = ["assetId"], onDelete = ForeignKey.CASCADE ) ] ) data class ConditionHistory( @PrimaryKey(autoGenerate = true) val historyId: Long = 0, val assetId: Long, val status: String, // GREEN, YELLOW, RED val checkedBy: String, val checkDate: String, val remarks: String? = null )

7.3.4 Members Table

@Entity(tableName = "members") data class Member( @PrimaryKey(autoGenerate = true) val memberId: Long = 0, val name: String, val role: String, val status: String, // Present, Absent, On Leave val bio: String, val responsibilities: String, // Comma-separated val imageUrl: String? = null )

7.3.5 Attendance Table

@Entity( tableName = "attendance", foreignKeys = [ ForeignKey( entity = Member::class, parentColumns = ["memberId"], childColumns = ["memberId"], onDelete = ForeignKey.CASCADE ) ] ) data class Attendance( @PrimaryKey(autoGenerate = true) val attendanceId: Long = 0, val memberId: Long, val date: String, // yyyy-MM-dd val status: String // Present, Absent, On Leave )

7.3.6 Users Table

@Entity(tableName = "users") data class User( @PrimaryKey(autoGenerate = true) val id: Long = 0, val uniqueId: String, // Unique school ID or teacher ID val name: String, val email: String, val passwordHash: String )

The application implements reactive data flow using Kotlin Flow and StateFlow:
